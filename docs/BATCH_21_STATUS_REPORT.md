## Feedback Scoring Algorithm

### Success Rate Calculation

```
success_rate = successful_actions / (total_actions - stubbed_actions)

Special cases:
- If all actions are stubbed: success_rate = 1.0
- If no actions exist: success_rate = 1.0 (no failures)
- Minimum value: 0.0 (all failures)
- Maximum value: 1.0 (all successes)
```

### Status Classification

| Status Value | Category | Counted As |
|-------------|----------|------------|
| `success`, `completed`, `ok` | Success | Successful execution |
| `failed`, `error`, `timeout`, `rejected` | Failure | Failed execution |
| `stubbed` | Stub | Excluded from success rate |
| Other values | Unknown | Flagged as issue |

### Anomaly Detection Patterns

1. **High Stub Usage** (≥50%)
   - Triggers: `stub_count / total_actions >= 0.5`
   - Indicates: System not fully implemented

2. **High Failure Rate** (≥30%)
   - Triggers: `failed_actions / total_actions >= 0.3`
   - Indicates: Systemic reliability issues

3. **Unknown Action Types**
   - Triggers: Action type not in `KNOWN_ACTION_TYPES`
   - Indicates: Unregistered or experimental actions

4. **Complete Failure** (all non-stub actions failed)
   - Triggers: `successful_actions == 0` AND `total > stubbed`
   - Indicates: CRITICAL system malfunction

5. **No Actions Executed**
   - Triggers: `total_actions == 0`
   - Indicates: Policy Brain or Executor not working

## Pattern Detection

### Stub Detection

The verifier identifies stubbed actions by checking for `status == "stubbed"`.

**Why it matters:**
- Stubs indicate incomplete implementation
- High stub ratios suggest the system needs development
- Stubs are excluded from success rate to avoid false positives

**Recommendations triggered:**
- "Consider implementing real modules for stubbed actions"
- "High stub count detected - prioritize implementing core action types"

### Failure Pattern Analysis

The verifier groups failures by action type to identify problem areas.

**Example:**
```
3 failures detected:
  - polymarket-fetch: API rate limit
  - polymarket-fetch: Network timeout
  - position-update: Database error

Recommendation: "Focus on fixing failures in: polymarket-fetch, position-update"
```

### Unknown Type Detection

Action types not in `KNOWN_ACTION_TYPES` trigger warnings.

**Known types:**
- health-check
- polymarket-fetch
- data-sync
- risk-calculation
- position-update
- market-analysis

**Why it matters:**
- Helps detect typos or experimental features
- Ensures action types are intentional
- Prompts registration of new types

## Safety Rules

### DRYRUN-Only Guarantees

1. **No Network Calls**
   - Module makes zero network requests
   - All operations are local file I/O

2. **No Action Execution**
   - Only reads and analyzes results
   - Never triggers or modifies actions

3. **Restricted File Access**
   - Operations limited to `state/` directory
   - Never modifies executor or policy modules
   - Never touches legacy Termux code

4. **Graceful Degradation**
   - Missing input files → generates feedback with empty data
   - Malformed JSON → handles safely, reports issue
   - Always produces output, even on errors

5. **No Data Destruction**
   - Only writes to `brain_feedback.json`
   - Never deletes or overwrites `brain_actions.json`

### Error Handling Philosophy

The verifier follows the "always-complete" philosophy:

- **Missing input file?** → Continue with empty action list
- **Malformed JSON?** → Log error, use empty data structure
- **Unknown status?** → Flag as issue, continue processing
- **Save failure?** → Return error code, but attempt was made

**Principle:** Better to provide partial feedback than to crash and provide nothing.

## Performance Characteristics

### Time Complexity
- **Load actions:** O(n) - single file read
- **Verify actions:** O(n) - single pass through actions
- **Detect anomalies:** O(1) - fixed checks
- **Generate recommendations:** O(n) - proportional to findings
- **Overall:** O(n) where n = number of actions

### Space Complexity
- **Memory usage:** O(n) - stores actions and feedback in memory
- **Disk usage:** O(n) - feedback file size proportional to action count

### Typical Performance
- **100 actions:** ~50ms
- **1,000 actions:** ~200ms
- **10,000 actions:** ~1.5s

## Known Limitations

1. **No Historical Tracking**
   - Current version analyzes single snapshot
   - Does not track trends over time
   - Future: Add time-series analysis

2. **Simple Anomaly Detection**
   - Uses threshold-based rules
   - No machine learning or pattern recognition
   - Future: Add ML-based anomaly detection

3. **No Action Prioritization**
   - Recommendations not prioritized by impact
   - All issues weighted equally
   - Future: Add severity/impact scoring

4. **Limited Context**
   - Cannot access external system state
   - Only knows what's in brain_actions.json
   - Future: Integrate with monitoring systems

5. **No Automatic Remediation**
   - Only suggests recommendations
   - Does not fix issues automatically
   - Future: Add auto-remediation hooks
